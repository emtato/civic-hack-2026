## Observed fields and implications

| Actual field | Import handling |
| --- | --- |
| `noticeId` | Preserve as the stable source-record ID; it does not by itself identify a unique underlying proposal. |
| `title`, `noticeDescription` | Preserve the original; descriptions contain HTML. Extract readable text and retain the evidence used for summaries/features. |
| `noticeDate` | Millisecond timestamp of notice publication; keep separate from meeting, deadline and decision dates. |
| `addressList` | Arrays with coordinate strings and addresses. 625 records contain at least one coordinate pair; the correctness and proposal relevance of those locations are not established by presence alone. |
| `topics`, `planningApplicationNumbers` | Useful for selection and matching. Normalize whitespace; treat ambiguous project matches as review work. |
| `backgroundInformationList`, `otherReferenceList` | Preserve linked official evidence; some information requires following these references. |
| `decisionBody` | Present in some records; allow missing values. Do not infer final approval from the named body. |
| `eventList` | Empty in all 648 returned records, including notices with meeting dates in their descriptions. An empty array must not become “no meeting.” |

Observed topic families include planning, heritage, transportation, licensing, financial matters and sale of City property. A notice's topic is not a full statement of its proposal or current status. The catalogue must exclude irrelevant notices and distinguish applications, proposed changes and already adopted decisions.
